LUCKY — On-chain Lottery with Chainlink VRF + Automation
=======================================================

Introduction
------------
Lucky is an on-chain lottery / raffle smart contract system that uses Chainlink VRF v2+ for secure randomness and Chainlink Automation for scheduling and round lifecycle management. Players can buy tickets (ERC-20 token or native ETH), the contract collects tickets per round, and Chainlink randomness selects first/second/third prize winners. The project is built to be upgradeable (UUPS) and includes local mocks and tests for development.

Key Features
------------
- Chainlink VRF v2+ integration for provably-fair randomness.
- Chainlink Automation-compatible keepers for automatically ending rounds and handling timeouts.
- Support for ERC-20 token payments (configured `allowedToken`) and native ETH payments.
- Upgradable contract pattern using OpenZeppelin UUPS.
- Round lifecycle: create rounds, deposit prize tokens, buy tickets, end round (randomness request), fulfill winners, automatic new round creation.
- Refund & failure handling when rounds fail (insufficient players or VRF failure).
- Admin controls: set ticket price, duration, waiting time, prize sizes, VRF parameters, forwarder address.

Technology Stack
----------------
- Smart Contracts: Solidity (>=0.8.24)
- Development & Testing: Hardhat (TypeScript tests in `test/`)
- OpenZeppelin: UUPS, ERC-20 interfaces and utilities
- Chainlink: VRF v2+ and Automation (Keepers)
- Mocks: local VRFCoordinatorV2_5Mock and MockToken (contracts/Mock)

How Lucky works (high-level)
----------------------------
1. Admin configures VRF parameters, allowed token, ticket price, prize amounts, duration, waiting time, and max tickets per user.
2. Admin deposits prize tokens for a round using `depositPrizeTokens(roundId, prizeTokenAddress)`.
3. Admin (or the contract itself) creates a round with `createRound(duration, waitingTime, ticketPrice)`.
4. Players buy tickets for the active round:
	- ERC-20 payment: approve the `allowedToken` and call `buyTickets(ticketCount)`.
	- Native ETH payment: call `buyTicketsWithNative{value: ...}(ticketCount)`.
5. When the round end time passes, Chainlink Automation (or an authorized forwarder) calls `performUpkeep` which ends the round and requests randomness from Chainlink VRF.
6. `fulfillRandomWords` (called internally after VRF callback) picks 3 distinct winners (first/second/third) and emits `RoundEnded`.
7. Winners can check/claim prizes via available helper functions; if rounds fail, players can claim refunds.

Primary contract API (selected)
-------------------------------
- `initialize(vrfCoordinator, keyHash, subscriptionId, allowedToken, dateTimeContract)` — initialize upgradeable contract.
- `setRound(...)`, `setRoundParameters(...)` — admin setters for round defaults.
- `depositPrizeTokens(roundId, prizeTokenAddress)` — admin deposits prize tokens for the round.
- `createRound(duration, waitingTime, ticketPrice)` — create a new round.
- `buyTickets(ticketCount)` — purchase tickets paid in `allowedToken` (requires ERC-20 approval).
- `buyTicketsWithNative(ticketCount)` — purchase tickets paid with ETH (payable).
- `checkUpkeep` / `performUpkeep` — Automation-compatible functions used to end rounds and detect timeouts.
- `claimRefund(roundId)` — player claims refund for failed rounds.
- `getRoundInfo(roundId)` / `checkOwnPrizes(roundId)` — view round and user-specific prize info.

Developer notes — local development & testing
-------------------------------------------
- Tests: run the test suite with Hardhat (TypeScript tests are in `test/`).

```powershell
# install deps (if not already)
npm install

# run tests and coverage in PowerShell
npx hardhat test
npx hardhat coverage
```

- Local mocks: use the contracts in `contracts/Mock/` (e.g., `VRFCoordinatorV2_5Mock.sol`, `MockToken.sol`) for testing VRF and token flows.
- Deployment: check `scripts/` for deployment helpers (Hardhat scripts written in TypeScript).

Security & design notes
-----------------------
- The contract uses UUPS upgradeability; keepers of the upgrade path (owner) must secure the upgrade key.
- VRF requests are tracked by `requestIdToRoundId` to map callback to the proper round.
- Rounds that fail or do not collect enough players are marked `FAILED` and support refunds and prize token refunds.
